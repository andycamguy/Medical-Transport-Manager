# CMH Scheduler v0.4.0 — deploy tonight

## What this version expects

- Flask application
- PostgreSQL database
- Render web service
- Render managed PostgreSQL
- HTTPS
- Authentication

The included `render.yaml` creates the web service and PostgreSQL database together.

## 1. Put the project in GitHub

Create a new GitHub repository, then upload the contents of this folder.

Do NOT upload:

- `.env`
- `instance/`
- `*.db`
- real patient information

## 2. Create the Render deployment

In Render:

1. Choose **New → Blueprint**.
2. Connect the GitHub repository containing this project.
3. Render should detect `render.yaml`.
4. Confirm that it will create:
   - `cmh-scheduler` web service
   - `cmh-scheduler-db` PostgreSQL database
5. Keep the plans in `render.yaml` for the first production deployment.
6. When Render asks for secret environment variables, set:

   `ADMIN_USERNAME`

   Example:

   `ben`

   `ADMIN_PASSWORD`

   Use a new strong password of at least 12 characters. Do NOT use the sample local-development password.

7. Deploy.

## 3. Wait for the health check

Render should report the web service as healthy.

The application has a public health endpoint:

`/health`

A successful response is:

`{"ok":true,"database":"ok"}`

## 4. First login

Open the HTTPS Render URL.

Log in with the `ADMIN_USERNAME` and `ADMIN_PASSWORD` values you supplied to Render.

Immediately go to **ACCOUNT** and change the password again if desired.

## 5. Create driver accounts

As the owner, open **USERS**.

Create a separate account for each driver and link the account to that driver's driver record.

Give each driver a unique password. Do not share the owner account.

## 6. Production settings already included

- `SECRET_KEY` is generated by Render.
- `COOKIE_SECURE=1` enables secure session cookies.
- `SEED_DEMO_DATA=0` prevents fictional demo patients from being inserted into production.
- CSRF protection is enabled.
- Login POST requests are rate limited.
- Passwords are stored as hashes.
- HTTP security headers are added.
- The database is PostgreSQL rather than a local file.
- The health check verifies the database connection.

## 7. Before real patient data

Do one complete test with fictional data first:

- Login
- Create patient
- Edit patient
- Create appointment
- Change appointment time
- Change estimated trip time
- Assign outbound driver
- Assign return driver
- Add trip
- Delete trip
- Change trip status
- Cancel appointment
- Reinstate appointment
- Log out
- Log back in
- Restart/redeploy the service
- Confirm the test data remains in PostgreSQL

Only after these tests pass should real operational data be considered.
